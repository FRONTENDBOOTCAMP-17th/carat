## 코드 상태 실측 (2026-07-07)

- `npx tsc --noEmit` — 통과(에러 0). 타입은 계속 깨끗합니다.
- `npx eslint .` — **에러·경고 0**. 지난 8건에서 완전히 정리됐습니다.
- `npm run build` — 통과. 백엔드 의존이 없는 구성이라 빌드·배포 리스크가 낮은 건 이 조의 강점입니다.

## 박현우

이번 delta에서 제일 눈에 띄는 건 Essential Collection의 인터랙티브 3D 뷰어(IRIS)와, 그걸 위해 히어로와 뷰어가 3D 씬 설정을 공유하도록 `RingScene.tsx`로 공통화한 부분입니다. 조명·재질·지오메트리·환경맵 구성을 한 곳에 모아두고 히어로는 스크롤 애니메이션 그룹으로, Essential 뷰어는 `OrbitControls`로 감싸 쓰는 구조인데, 같은 모델을 두 화면에서 쓰면서 셋업을 복붙하지 않은 게 좋습니다. 무엇보다 각 결정마다 "왜 이 값인지"를 주석으로 남겨둔 밀도가 인상적입니다. 톤매핑을 ACES 대신 Khronos PBR Neutral로 고른 이유, 무채색 환경맵 위에서 골드를 완전 거울로 두면 "색 필터 씌운 플라스틱"처럼 보여서 roughness를 살짝 준 이유, 라이트 모드에서 다크 리플렉터를 넣어야 무색 보석이 흰 플라스틱으로 안 보이는 이유까지 — 이런 설명은 나중에 본인이 코드를 다시 열었을 때도, 채용담당자가 레포를 봤을 때도 "이 사람은 눈에 보이는 결과를 근거로 판단하는 사람"이라는 인상을 정확히 줍니다. 디자이너 출신의 강점이 코드 주석에까지 드러나는 흔치 않은 경우라 생각합니다.

성능 처리도 신경 쓴 게 보입니다. 테마 전환이 렉 걸리던 걸, 마운트 시점에 라이트·다크 환경맵 4장과 PMREM 2장을 미리 구워두고 토글은 텍스처 참조만 바꾸도록 정리한 부분(`useStudioEnvMaps`)이 그렇고, 화면에서 벗어나면 `IntersectionObserver`로 `frameloop`을 멈춰 rAF 루프가 계속 프레임을 잡아먹지 않게 한 것도 그렇습니다. 3D는 잘못 다루면 발표장에서 바로 버벅이는 영역인데, 그 지점들을 미리 짚어둔 게 좋습니다.

모바일 파이어폭스 폴백(`canRenderRingScene`)도 세심합니다. Gecko/Android가 WebGL2를 지원한다고 보고하지만 `MeshRefractionMaterial`이 거기선 보석을 하얗게 날려버려서, UA를 좁게(`Firefox/` + `Android`, 단 데스크탑 Firefox와 iOS FxiOS는 제외) 잡아 폴백을 띄우도록 한 판단이 정확합니다. 이런 건 실제로 그 환경에서 깨지는 걸 보지 않으면 못 짚는 부분이라, 직접 확인하고 처리한 걸로 보입니다.

가볍게 두 가지만 짚어둘게요. 어느 것도 발표를 막는 수준은 아닙니다.

- **[제안] WebGL 지원 판정의 하이드레이션 처리.** `hasWebGL = useMemo(() => canRenderRingScene(), [])`가 서버 렌더에서는 `true`(window 없음)를 주고, 클라이언트에서 다시 계산될 때 Gecko/Android면 `false`로 뒤집힙니다. 서버가 그린 `<Canvas>` 자리를 클라이언트가 폴백 `<div>`로 교체하게 되어 그 좁은 환경에서 하이드레이션 불일치가 생길 수 있습니다. 실제로 문제되는 브라우저가 극소수라 지금 당장 급한 건 아니지만, `mounted` 플래그로 클라이언트에서 한 번 확정한 뒤 판정하면 서버·클라이언트가 처음엔 똑같이 폴백을 그리다 마운트 후에만 3D로 올라가서 깔끔해집니다. 가이드에 예시를 적어뒀습니다.
- **[사소] 히어로 첫 프레임의 워드마크 레이어.** 스크롤 0 지점에서 큰 고스트 "PRISME"와 그 위 작은 "PRISME" 타이틀, 그리고 서브카피가 겹쳐 보이는데, 밝은 다이아몬드 위에 회색 서브카피가 얹히다 보니 대비가 살짝 낮게 잡히는 순간이 있습니다. 의도한 에디토리얼 레이어링이면 그대로 둬도 되지만, 발표 프로젝터에서 밝기가 뜨면 서브카피가 더 안 읽힐 수 있으니 그 한 줄만 살짝 진하게 두는 것도 고려해볼 만합니다.

한 가지 관찰만 덧붙이면, 이번 빌드에서 라우트가 이전의 전부 Static(○)에서 전부 Dynamic(ƒ)으로 바뀌어 있습니다. 언어·테마를 쿠키로 읽느라 그런 걸로 보이는데 배포에는 아무 문제가 없습니다. 다만 콘텐츠가 고정된 페이지(예: /faq, /shipping)는 정적으로 빠질 여지가 있어서, 발표 이후 여유가 생기면 그 부분만 떼어 CDN 캐시를 태우는 정도로 다듬어도 좋겠다는 정도의 메모입니다. 지금 건드릴 일은 아닙니다.

## 발표 직전 체크리스트

내일 데모에서 3D가 안정적으로 보이는 게 이 조의 핵심이라, 그쪽에 맞춘 점검만 짧게 남깁니다.

1. **배포본 시크릿 창 워크스루 1회.** 발표 직전에 `project-carat.vercel.app`을 시크릿 창으로 열어 홈 → Essential 3D → 검색 → 상세까지 한 바퀴 걸어보며 깨진 데가 없는지 확인하세요. 캐시 없는 첫 방문에서 로딩이 어떻게 보이는지가 결국 심사 때와 똑같은 상황입니다.
2. **3D가 안 뜰 때 대비.** 발표장 네트워크나 프로젝터 GPU가 변수라, 로컬에서 `npm run build && npm run start`로 띄운 백업을 하나 준비해두면 안심입니다. WebGL 폴백과 `prefers-reduced-motion` 화면도 스크린샷으로 미리 확보해두면 최악의 경우 정지 이미지로라도 설명할 수 있습니다.
3. **모바일 뷰 하나 준비.** Essential 3D 뷰어가 모바일에서 도는 장면은 발표에서 강한 한 방이 됩니다. 실제 기기 하나로 켜두거나 모바일 캡처를 슬라이드에 넣어두세요.

전체적으로 지난 이틀 밀도가 좋았습니다. 화면이라는 분명한 무기를 이제 배포와 3D 인터랙션으로 "보이게" 만들어 뒀으니, 남은 건 발표장에서 그게 흔들림 없이 나오도록 하는 것뿐이라 생각합니다. 화이팅입니다.
