## 1. Vercel 배포 + README 데모 섹션

이 프로젝트는 위시리스트·로그인이 `localStorage`, 검색은 `products.json`을 쓰는 구조라 백엔드 의존이 없습니다. 설정할 환경변수가 없으니 그대로 배포하면 바로 뜹니다.

**배포 절차**

1. [vercel.com](https://vercel.com)에 GitHub 계정으로 로그인합니다.
2. "Add New Project" → 이 저장소 선택 → 프레임워크가 Next.js로 자동 인식되는지 확인하고 그대로 Deploy를 누릅니다.
3. 몇 분 뒤 `https://프로젝트명.vercel.app` 같은 주소가 나오면, 그 주소를 직접 눌러서 홈·컬렉션·상세·검색까지 한 번씩 클릭해보고 깨지는 화면이 없는지 확인합니다.
4. main 브랜치에 커밋을 푸시할 때마다 자동으로 재배포되니, 이후로는 신경 쓸 일이 거의 없습니다.

**README 최상단에 추가할 내용**

```md
# PRISME

## 라이브 데모
https://prisme-carat.vercel.app

가상의 주얼리 브랜드 PRISME를 주제로 제작한 프론트엔드 파이널 프로젝트입니다.
```

## 2. `set-state-in-effect` 경고 8건 처리

지금 걸리는 8건은 전부 마운트 시점에 `localStorage`를 읽어 state를 동기화하는 자리입니다. 예를 들어 `src/context/ThemeContext.tsx:27-30`을 보면 이런 구조입니다.

```tsx
useEffect(() => {
  const stored = localStorage.getItem("prisme_theme");
  const hasUserPref = stored === "light" || stored === "dark";
  const resolved = hasUserPref ? stored : detectOsTheme();
  setThemeState(resolved); // ← 여기서 걸림
  document.documentElement.setAttribute("data-theme", resolved);
  ...
}, []);
```

`localStorage`는 브라우저에만 있고 서버에는 없기 때문에, 서버에서 렌더링한 결과와 클라이언트에서 처음 그리는 결과가 다를 수 있습니다(hydration mismatch). 그래서 일단 서버 기준 값으로 그려두고, 마운트된 다음에 `useEffect`로 실제 값을 다시 읽어와 갱신하는 방식을 쓴 건데, 이건 흔히 쓰이는 패턴이고 실제로 문제도 없습니다. 다만 Next.js가 이번에 새로 추가한 lint 규칙이 "effect 안에서 곧바로 setState 하는 패턴"을 전부 경고로 잡다 보니, 의도적으로 짠 코드인데도 빨간 줄이 뜨는 상황입니다.

해결 방법은 두 가지입니다.

**방법 A — 가장 빠름: 사유 주석 + 줄 단위 disable**

```tsx
useEffect(() => {
  const stored = localStorage.getItem("prisme_theme");
  const hasUserPref = stored === "light" || stored === "dark";
  const resolved = hasUserPref ? stored : detectOsTheme();
  // localStorage는 서버에 없어 SSR 시 알 수 없으므로, 마운트 후 클라이언트 값으로 동기화합니다.
  // eslint-disable-next-line react-hooks/set-state-in-effect
  setThemeState(resolved);
  document.documentElement.setAttribute("data-theme", resolved);
  ...
}, []);
```

빠르게 처리하고 싶다면 이 방법으로 8곳 전부(`LoginModal.tsx:69`, `Navbar.tsx:22`, `SearchModal.tsx:27`·`:32`, `LanguageContext.tsx:34`, `ThemeContext.tsx:29` 외)에 같은 패턴을 적용하면 됩니다.

**방법 B — 더 정석: `useSyncExternalStore`로 이관**

React가 외부 저장소(브라우저 API, localStorage 등)를 구독할 때 쓰라고 제공하는 훅입니다. `useEffect` + `useState` 조합보다 hydration을 더 안전하게 처리해줍니다.

```tsx
function getSnapshot() {
  const stored = localStorage.getItem("prisme_theme");
  return stored === "light" || stored === "dark" ? stored : detectOsTheme();
}

function getServerSnapshot() {
  return "dark"; // 서버 기본값
}

const theme = useSyncExternalStore(subscribeToNothing, getSnapshot, getServerSnapshot);
```

지금 시점(마감 며칠 전)에 구조를 바꾸는 건 리스크 대비 이득이 크지 않으니, 방법 A로 우선 정리하고 여유가 되면 방법 B를 검토하는 정도를 권합니다. 둘 다 강제 사항은 아니고, 지금처럼 둬도 동작에는 문제가 없습니다.

## 3. 카드 클릭 영역을 `<Link>`로 바꾸기

`ProductCard.tsx`와 `CollectionCard.tsx`가 거의 같은 구조라 `ProductCard.tsx` 기준으로 설명하면, 지금은 이렇게 돼 있습니다.

```tsx
// src/components/ProductCard.tsx:30-37 (현재)
<article
  className="group cursor-pointer"
  aria-label={`${name}${category ? `, ${category}` : ""}`}
  role="link"
  tabIndex={0}
  onClick={() => router.push(navigateTo)}
  onKeyDown={(e) => { if (e.key === "Enter") router.push(navigateTo); }}
>
```

동작은 잘 되지만, 진짜 `<a>` 태그가 아니라서 가운데 클릭으로 새 탭 열기가 안 되고 브라우저 컨텍스트 메뉴("새 탭에서 열기")도 못 씁니다. `<Link>`로 감싸는 구조로 바꾸면 이 모든 게 공짜로 딸려옵니다.

```tsx
import Link from "next/link";

<Link href={navigateTo} className="group cursor-pointer block" aria-label={...}>
  <div className="relative mb-4">
    <div className="aspect-square bg-surface-input" role="img" aria-label={...} />
    <button
      onClick={handleWishlist}
      className="absolute top-2 right-2 ..."
      aria-label={...}
      aria-pressed={inWishlist}
    >
      <Heart ... />
    </button>
  </div>
  {category && <p ...>{category}</p>}
  <h3 ...>{name}</h3>
  {description && <p ...>{description}</p>}
</Link>
```

`handleWishlist` 안의 `e.stopPropagation()`은 이미 있으니 그대로 두면 됩니다. `<Link>` 안에 `<button>`이 들어가는 구조는 시맨틱상 완전히 깔끔하진 않지만(인터랙티브 요소 중첩), 실제 브라우저·스크린리더 동작에는 문제가 없고 많은 프로덕션 서비스에서도 쓰는 패턴이라 지금 단계에서는 이 정도로 충분합니다. `CollectionCard.tsx:27-33`도 같은 방식으로 고치면 됩니다.

## 이력서·자기소개서로 연결하는 법

지금까지 만든 것 중 몇 가지는 "무엇을 왜 그렇게 만들었는지"만 한두 문장으로 정리해두면 그대로 이력서 프로젝트 설명이나 기술 면접 답변이 됩니다.

- **리팩토링 경험**: "14개 페이지에 반복되던 레이아웃 코드를 `PageShell` 컴포넌트 하나로 묶어 168줄을 제거했고, 서버/클라이언트 컴포넌트 경계를 명확히 나눴습니다." — 이런 식으로 커밋 하나(`9ea2144`)를 근거로 구체적인 숫자와 함께 설명할 수 있으면 "왜 리팩토링했는지"까지 답할 준비가 된 겁니다.
- **접근성(a11y)**: 디자이너 출신이라는 배경과 가장 잘 붙는 강점입니다. Breadcrumb의 WCAG 내비게이션 패턴, contact 폼의 `aria-invalid`/`aria-describedby`/`role="alert"`, SearchModal의 combobox 패턴처럼 "동작만 되게 만든 게 아니라 스크린리더 사용자까지 고려해서 만들었다"는 걸 구체적인 예시 하나 정도는 바로 설명할 수 있게 준비해두면 좋습니다.
- **성능·예외 처리 감각**: CustomCursor에서 Firefox 충돌을 발견해 예외 처리한 것, WebGL 미지원 환경을 위한 fallback을 마련한 것처럼 "안 되는 경우를 미리 찾아서 처리한" 사례들도 꼼꼼함을 보여주는 좋은 소재입니다.

README의 "기술 스택" 항목에도 로고만 나열하기보다, 이런 판단 하나씩을 한 줄로 붙여두면 코드를 안 열어봐도 사고 과정이 드러납니다.
